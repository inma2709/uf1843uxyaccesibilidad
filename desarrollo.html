Una página web no está terminada cuando conseguimos que se vea correctamente en nuestro navegador. También debemos comprobar que su código es adecuado, que las personas pueden utilizarla y que no presenta barreras de accesibilidad evitables.

Durante los temas anteriores hemos estudiado la accesibilidad, la usabilidad, la planificación y el diseño visual. Ahora vamos a unir esos conocimientos para aprender a desarrollar y evaluar una página web.

Imagina que has creado la web de una biblioteca. El menú funciona con el ratón, el formulario permite enviar una solicitud y las imágenes se muestran correctamente.

¿Significa eso que la web es accesible? No necesariamente. Todavía necesitamos comprobar si puede utilizarse con teclado, si los campos tienen etiquetas comprensibles y si el contenido mantiene su funcionalidad al ampliarlo.

Idea fundamental: desarrollar una web de calidad implica implementar, comprobar, detectar problemas, corregirlos y volver a evaluar. La accesibilidad es un proceso continuo.

Qué aprenderás en este tema

Aprenderás a reconocer errores frecuentes de implementación, utilizar herramientas de validación y realizar comprobaciones manuales de accesibilidad.

También conocerás Easy Checks, la metodología WCAG-EM y una forma sencilla de documentar problemas y mejoras.

1. Aplicar la accesibilidad al escribir código

La accesibilidad comienza con decisiones aparentemente sencillas: elegir la etiqueta HTML adecuada, asociar las etiquetas de los formularios, conservar el foco visible y permitir que los contenidos se adapten a diferentes pantallas.

Vamos a revisar algunos errores habituales y sus soluciones.

1.1. Utilizar HTML semántico

HTML ofrece etiquetas que comunican el significado de los elementos. Por ejemplo, header, nav, main y footer ayudan a organizar la estructura de un documento.

Cuando utilizamos estas etiquetas correctamente, facilitamos la interpretación del contenido por parte del navegador y las tecnologías de apoyo.

Ejemplo de estructura semántica

Ver ejemplo de código
<header>

  <h1>Biblioteca municipal</h1>

</header>

<nav aria-label="Navegación principal">

  <a href="index.html">Inicio</a>

  <a href="catalogo.html">Catálogo</a>

</nav>

<main>

  <h2>Consulta nuestro catálogo</h2>

  <p>

    Encuentra libros y otros recursos.

  </p>

</main>

<footer>

  <p>Biblioteca municipal</p>

</footer>

Este fragmento representa el contenido del body de una página. No es necesario utilizar div para todo: cuando existe una etiqueta semántica adecuada, normalmente es preferible.

1.2. Crear botones que funcionen con teclado

Un error frecuente consiste en utilizar elementos sin semántica interactiva para representar botones.

Ejemplo problemático

Ver ejemplo de código
<div onclick="guardar()">

  Guardar cambios

</div>

Este elemento responde al clic del ratón, pero no incorpora por defecto el comportamiento de teclado de un botón.

Alternativa recomendada

Ver ejemplo de código
<button type="button"

        onclick="guardar()">

  Guardar cambios

</button>

El elemento button dispone de semántica propia y puede activarse mediante teclado. En ambos ejemplos se supone que existe una función JavaScript llamada guardar().

Comprueba: ¿puedes llegar al botón pulsando Tab y activarlo mediante Enter o Espacio?

1.3. Mantener el foco visible

El foco permite identificar qué elemento está preparado para recibir la interacción mediante teclado.

Eliminar su indicador visual sin ofrecer una alternativa puede impedir que una persona sepa dónde se encuentra.

CSS problemático

Ver ejemplo de código
button:focus {

  outline: none;

}

Esta regla elimina el contorno de foco del botón. Si no existe otro indicador visible, se genera una barrera de navegación.

CSS recomendado

Ver ejemplo de código
button:focus-visible,

a:focus-visible {

  outline: 3px solid #174ea6;

  outline-offset: 3px;

}

:focus-visible permite aplicar estilos cuando corresponde mostrar un indicador de foco visible.

El color elegido debe contrastar suficientemente con los fondos sobre los que aparece.

1.4. Proporcionar alternativas para imágenes

Una imagen informativa necesita una alternativa textual que comunique su información o propósito.

Ejemplo

Ver ejemplo de código
<img

  src="horario.png"

  alt="Biblioteca: lunes a viernes,

       de 9:00 a 20:00 horas"

>

Si una imagen es exclusivamente decorativa, podemos utilizar alt="".

La alternativa correcta depende de la función de la imagen dentro de la página.

1.5. Crear enlaces descriptivos

Los enlaces deben permitir comprender su destino o función.

Ejemplo poco claro

Ver ejemplo de código
<a href="guia.pdf">

  Haz clic aquí

</a>

Alternativa recomendada

Ver ejemplo de código
<a href="guia.pdf">

  Descargar la guía de matrícula (PDF)

</a>

El segundo enlace permite saber qué documento se abrirá o descargará, incluso cuando se lee fuera del contexto del párrafo.

1.6. Asociar etiquetas a los formularios

Un campo de formulario necesita un nombre comprensible. El atributo placeholder puede aportar un ejemplo, pero no sustituye una etiqueta.

Ver ejemplo de código
<label for="correo">

  Correo electrónico

</label>

<input

  type="email"

  id="correo"

  name="correo"

  autocomplete="email"

  required

>

El atributo for del label coincide con el id del campo.

También debemos indicar los campos obligatorios de manera comprensible y explicar los errores de validación.

1.7. Diseñar contenido flexible

El contenido debe adaptarse al espacio disponible y permitir ampliar el texto sin perder información o funcionalidad.

Podemos comenzar con reglas sencillas de CSS:

Ver ejemplo de código
body {

  font-size: 1rem;

  line-height: 1.5;

}

img {

  max-width: 100%;

  height: auto;

}

rem es una unidad relativa de tamaño. En las imágenes, max-width: 100% evita que superen la anchura de su contenedor cuando son más grandes que él.

Estas reglas ayudan a crear diseños adaptables, pero no garantizan por sí solas que todo el contenido cumpla los criterios de reflow.

1.8. Respetar las preferencias de movimiento

Las animaciones y transiciones pueden resultar molestas o provocar dificultades a determinadas personas.

CSS permite consultar si el sistema ha indicado una preferencia por reducir el movimiento.

Ver ejemplo de código
@media (prefers-reduced-motion: reduce) {

  .elemento-animado {

    animation: none;

    transition: none;

  }

}

En este ejemplo, .elemento-animado representa un componente que normalmente contiene animaciones o transiciones.

La solución debe adaptarse a cada componente para no eliminar información o funcionalidad esencial.

Recuerda: evita iniciar automáticamente contenido multimedia con sonido y proporciona controles adecuados para pausar o detener contenido cuando corresponda.

1.9. Utilizar ARIA con criterio

ARIA permite comunicar información adicional sobre determinados componentes a las tecnologías de apoyo.

Sin embargo, ARIA no convierte automáticamente un elemento en accesible.

Por ejemplo, añadir role="button" a un div no incorpora por sí solo el comportamiento de teclado de un botón nativo.

Regla práctica: utiliza primero HTML semántico. Recurre a ARIA cuando sea necesario, comprueba su efecto y no lo utilices para sustituir comportamientos nativos que ya ofrece HTML.

1.10. Cómo crear una página que pueda utilizarse sin ratón

Hasta ahora hemos visto que los controles deben funcionar con teclado. Pero ¿qué tenemos que programar para conseguirlo? La respuesta es sencilla: empezar por los elementos HTML nativos. Los enlaces, botones y campos de formulario ya incorporan comportamientos de teclado proporcionados por el navegador.

Qué teclas se utilizan

Interacciones habituales mediante teclado
TeclaQué hace normalmente
TabAvanza entre los controles que pueden recibir el foco.
Shift + TabRetrocede al control anterior.
EnterActiva enlaces y botones; también puede enviar un formulario según el contexto.
EspacioActiva botones y cambia el estado de las casillas de verificación cuando tienen el foco.
FlechasPermiten elegir opciones en controles como los grupos de botones de radio.

No todas las teclas funcionan igual en todos los elementos. Por ejemplo, un enlace se activa normalmente con Enter, mientras que un botón admite Enter y Espacio. Este comportamiento es una de las ventajas de utilizar las etiquetas correctas.

La regla principal: no reinventar los controles

Este elemento no es un botón accesible por defecto:

Ver ejemplo de código
<div onclick="guardar()">Guardar</div>

En cambio, este sí incorpora semántica y activación mediante teclado:

Ver ejemplo de código
<button type="button" onclick="guardar()">
  Guardar
</button>

En ambos fragmentos se presupone una función llamada guardar(). La diferencia importante es que el botón nativo ya es enfocable y responde al teclado sin tener que programar eventos adicionales.

Ejemplo completo: una página que funciona con teclado

Crea un archivo llamado teclado.html, copia el siguiente ejemplo y ábrelo en un navegador. Incluye un enlace, un campo, una casilla y un botón con una respuesta visible. El evento click del botón se ejecuta también cuando este se activa mediante Enter o Espacio.

Ver ejemplo de código
<!doctype html>
<html lang="es">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Práctica de teclado</title>
  <style>
    body {
      font: 1rem/1.5 system-ui, sans-serif;
      max-width: 38rem;
      margin: 2rem auto;
      padding: 0 1rem;
    }
    label { display: block; margin: 1rem 0; }
    button { padding: .6rem 1rem; }
    a:focus-visible,
    input:focus-visible,
    button:focus-visible {
      outline: 3px solid #174ea6;
      outline-offset: 3px;
    }
  </style>
</head>
<body>
  <main id="contenido">
    <h1>Prueba de navegación con teclado</h1>
    <a href="#formulario">Ir al formulario</a>

    <form id="formulario">
      <label for="nombre">Tu nombre</label>
      <input id="nombre" name="nombre" required>

      <label>
        <input type="checkbox" id="acepto">
        He leído las instrucciones
      </label>

      <button type="submit">Mostrar saludo</button>
    </form>

    <p id="mensaje" role="status"></p>
  </main>

  <script>
    const formulario = document.querySelector('#formulario');
    const mensaje = document.querySelector('#mensaje');

    formulario.addEventListener('submit', (evento) => {
      evento.preventDefault();
      const nombre = document.querySelector('#nombre').value.trim();
      mensaje.textContent = `Hola, ${nombre}. Formulario enviado.`;
    });
  </script>
</body>
</html>

Observa que no necesitamos escuchar keydown para activar el botón: el navegador convierte la activación mediante teclado en el comportamiento habitual del control. La validación nativa impide enviar el formulario si el nombre está vacío. La casilla es solo un elemento de práctica y no condiciona el envío.

Actividad: comprueba y mejora la navegación

Objetivo: comprobar que una interfaz sencilla puede utilizarse sin ratón y reconocer cómo actúa el foco.

  1. Abre teclado.html y deja de usar el ratón.
  2. Pulsa Tab hasta el enlace y actívalo con Enter.
  3. Accede al campo de nombre, escribe un texto y continúa con Tab.
  4. Marca y desmarca la casilla mediante Espacio.
  5. Activa «Mostrar saludo» con Enter o Espacio y comprueba el mensaje.
  6. Retrocede con Shift + Tab y comprueba que siempre ves dónde está el foco.
  7. Elimina temporalmente los estilos de :focus-visible y observa el indicador que proporciona el navegador. Después recupéralos.

Resultado esperado: puedes completar la interacción sin ratón, entiendes qué elemento tiene el foco y sabes distinguir entre el comportamiento nativo de HTML y la lógica JavaScript.

¿Cuándo hacen falta eventos de teclado en JavaScript?

Normalmente no hacen falta para enlaces, botones o campos HTML nativos. Sí pueden ser necesarios en componentes personalizados complejos, como determinados menús o cuadros de diálogo, pero deben seguir los patrones de interacción apropiados y probarse con tecnologías de apoyo.

El atributo tabindex="0" puede incorporar un elemento al orden de tabulación, pero no lo convierte en un botón ni añade por sí solo las teclas de activación. Evita valores positivos como tabindex="1", que pueden generar un orden de navegación inesperado. tabindex="-1" permite enfocar mediante JavaScript ciertos elementos sin añadirlos al recorrido normal de Tab.

Regla para recordar: usa enlaces para navegar, botones para ejecutar acciones y controles nativos para introducir datos. Mantén un orden de HTML lógico y un foco visible. Después comprueba toda la tarea sin ratón.

2. Herramientas para comprobar una página web

Existen herramientas que nos ayudan a detectar errores de marcado, contrastes insuficientes y determinados problemas de accesibilidad.

Es importante elegir la herramienta adecuada para cada comprobación. No todas analizan lo mismo ni ofrecen el mismo tipo de resultados.

Importante: ninguna herramienta automática puede determinar por sí sola que una página cumple todos los requisitos de accesibilidad. Sus resultados deben interpretarse y complementarse con otras pruebas.

2.1. Nu HTML Checker: validar el código HTML

El Nu HTML Checker permite detectar problemas en la estructura y sintaxis del HTML.

Por ejemplo, puede informar de etiquetas mal utilizadas, atributos no permitidos o elementos obsoletos.

Abrir Nu HTML Checker

Cómo utilizarlo

  1. Abre la herramienta.
  2. Introduce la URL de una página pública, carga un archivo o pega el código HTML, según la opción disponible.
  3. Ejecuta la comprobación.
  4. Lee los errores y advertencias.
  5. Corrige los problemas identificados.
  6. Repite la validación.

Ejemplo: atributo obsoleto

En materiales antiguos puedes encontrar código como:

Ver ejemplo de código
<p align="center">

  Bienvenido

</p>

El atributo align utilizado así es obsoleto en HTML moderno. La presentación debe realizarse mediante CSS.

HTML recomendado

Ver ejemplo de código
<p class="texto-centrado">

  Bienvenido

</p>

CSS

Ver ejemplo de código
.texto-centrado {

  text-align: center;

}

Validar HTML ayuda a detectar problemas técnicos, pero no demuestra que la página cumpla las WCAG.

2.2. WebAIM Contrast Checker

Esta herramienta comprueba la relación de contraste entre dos colores.

Es especialmente útil cuando estamos definiendo los colores de textos y fondos.

Abrir WebAIM Contrast Checker

Cómo utilizarla

  1. Introduce el color del texto.
  2. Introduce el color del fondo.
  3. Observa la relación de contraste.
  4. Comprueba el resultado correspondiente al tamaño del texto y nivel WCAG.
  5. Ajusta los colores si el contraste es insuficiente.

En el tema de accesibilidad hemos realizado una actividad guiada con esta herramienta.

2.3. WAVE: detectar posibles barreras

WAVE es una herramienta de evaluación que presenta indicadores de accesibilidad sobre la propia página analizada.

Permite localizar determinados errores, advertencias y elementos estructurales que conviene revisar.

Abrir WAVE

Cómo utilizarla

  1. Abre WAVE.
  2. Introduce la URL de una página pública.
  3. Ejecuta el análisis.
  4. Revisa los indicadores que aparecen.
  5. Selecciona una incidencia.
  6. Localiza el elemento afectado y estudia su contexto.
  7. Propón una corrección cuando corresponda.

WAVE dispone también de extensiones de navegador que pueden resultar útiles para analizar páginas no accesibles mediante una URL pública.

Consultar extensión WAVE

No todas las alertas representan automáticamente un incumplimiento. Es necesario interpretar el resultado.

2.4. TAW: análisis automático de accesibilidad web

TAW (Test de Accesibilidad Web) permite analizar una página web y detectar posibles problemas de accesibilidad tomando como referencia las pautas WCAG.

Abrir TAW — Test de Accesibilidad Web

Cómo realizar un análisis

  1. Abre TAW e introduce la dirección de la página.
  2. Utiliza una URL pública accesible desde Internet. Una ruta local de tu ordenador, como C:\proyecto\index.html, no se puede analizar desde el servicio online.
  3. Si la interfaz ofrece opciones de configuración, selecciona el nivel que deseas revisar, por ejemplo AA.
  4. Inicia el análisis y espera a que se genere el informe.
  5. Revisa los problemas detectados y las comprobaciones que requieren una revisión manual.
  6. Comprueba cada aviso en su contexto, corrige los problemas confirmados y vuelve a analizar la página.
Importante: un informe sin errores automáticos no certifica que una página sea accesible. TAW no puede determinar por sí sola si todos los requisitos se cumplen; completa el análisis con pruebas manuales, como la navegación con teclado y la revisión del contenido.

Actividad práctica: analiza una página con TAW

  1. Elige una página pública que puedas revisar.
  2. Analízala con TAW y anota los errores y avisos que aparecen.
  3. Selecciona un resultado y comprueba en la página si representa un problema real.
  4. Anota qué comprobaciones necesitan intervención manual y propón una corrección para un problema confirmado.

2.5. Lighthouse: auditoría integrada en Chrome

Lighthouse es una herramienta de auditoría incluida en las herramientas de desarrollo de Google Chrome.

Permite analizar accesibilidad y otros aspectos técnicos, como rendimiento, buenas prácticas y SEO.

Documentación oficial de Lighthouse

Cómo utilizar Lighthouse

  1. Abre en Chrome la página que deseas analizar.
  2. Pulsa F12 o abre las herramientas de desarrollo.
  3. Busca la pestaña Lighthouse. Si no aparece, consulta las herramientas adicionales.
  4. Selecciona la categoría Accessibility.
  5. Ejecuta la auditoría mediante el botón disponible.
  6. Examina la puntuación y las incidencias detectadas.
  7. Corrige un problema y vuelve a ejecutar el análisis.

Los nombres de algunos botones pueden cambiar entre versiones de Chrome.

Atención: una puntuación alta de Lighthouse no significa que la web cumpla automáticamente las WCAG.

2.6. axe DevTools

axe DevTools es una herramienta de evaluación de accesibilidad que puede utilizarse como extensión del navegador.

Permite identificar determinados problemas y consultar información que ayuda a investigarlos y corregirlos.

Consultar axe DevTools

Uso inicial

  1. Instala la extensión desde una fuente oficial.
  2. Abre la página que analizarás.
  3. Accede a las herramientas de desarrollo.
  4. Abre axe DevTools.
  5. Ejecuta el análisis disponible.
  6. Revisa los problemas y los elementos afectados.

Algunas funciones pueden depender de la edición y licencia utilizadas.

2.7. Accessibility Insights

Accessibility Insights ofrece herramientas de ayuda para evaluar accesibilidad, incluyendo comprobaciones automáticas y recorridos de revisión guiada.

Puede ser útil para aprender a combinar la detección automática con comprobaciones manuales.

Consultar Accessibility Insights

Resumen: ¿qué herramienta elegir?

Herramientas habituales de revisión web
Herramienta Uso principal Cuándo utilizarla

Contrast Checker Comprobar contraste entre colores. Al definir y revisar la paleta de la interfaz.

3. Herramientas antiguas y alternativas actuales

El desarrollo web evoluciona continuamente. Por eso es normal encontrar manuales, artículos y tutoriales que mencionan aplicaciones utilizadas hace años.

Algunas herramientas dejan de actualizarse, presentan problemas de compatibilidad o se basan en versiones anteriores de los estándares.

Esto no significa que debamos descartar automáticamente toda la información antigua. Primero necesitamos distinguir entre los conocimientos que siguen siendo válidos y las herramientas concretas que han cambiado.

HERA: un ejemplo histórico

HERA es una herramienta desarrollada por la Fundación Sidar que facilitaba la revisión de accesibilidad de páginas web.

Está vinculada históricamente a las pautas WCAG 1.0 y a procedimientos de revisión que requieren interpretación humana.

Por ese motivo puede aparecer en documentación de accesibilidad publicada hace tiempo.

Sin embargo, al tratarse de una herramienta antigua, su disponibilidad, compatibilidad y pertinencia para evaluar estándares actuales deben comprobarse.

Para una revisión actual podemos utilizar herramientas como WAVE, Lighthouse, axe DevTools o Accessibility Insights, junto con pruebas manuales.

Estas alternativas no generan necesariamente los mismos informes ni realizan exactamente las mismas comprobaciones que HERA.

Para conocer su contexto histórico puedes consultar la información sobre HERA publicada por Fundación Sidar .

Cómo reconocer una herramienta que necesita revisión

Antes de utilizar una aplicación encontrada en un artículo o manual, conviene preguntarse:

  1. ¿Cuál es su página oficial?
  2. ¿Sigue estando disponible y funciona correctamente?
  3. ¿Qué estándares utiliza como referencia?
  4. ¿Se mantiene y es compatible con los navegadores actuales?
  5. ¿Qué tipo de comprobaciones realiza?
  6. ¿Qué limitaciones presenta?
  7. ¿Existe una alternativa más adecuada para mi objetivo?
Idea profesional: lo importante no es aprender a depender de una aplicación concreta, sino comprender qué necesitamos comprobar y saber elegir herramientas adecuadas para hacerlo.

Actividad: compara dos herramientas

Objetivo: aprender a seleccionar herramientas de accesibilidad de forma razonada.

  1. Elige dos herramientas explicadas en este manual.
  2. Consulta sus páginas oficiales.
  3. Identifica qué comprueba cada una.
  4. Indica si necesita instalación.
  5. Examina qué limitaciones presenta.
  6. Explica cuál utilizarías para revisar una web sencilla y por qué.

Resultado esperado: una comparación breve que justifique tu elección, sin limitarse a enumerar nombres.

4. Pruebas manuales: comprobar lo que una herramienta no ve

Las herramientas automáticas son útiles, pero existen aspectos que necesitan una revisión humana.

Por ejemplo, una herramienta puede detectar que una imagen tiene atributo alt, pero no siempre puede determinar si la descripción transmite correctamente su significado.

Por eso debemos realizar pruebas manuales.

4.1. Navegación con teclado

  1. Abre la página.
  2. Deja de utilizar el ratón.
  3. Pulsa Tab para avanzar.
  4. Utiliza Shift + Tab para retroceder.
  5. Comprueba que el foco es visible.
  6. Intenta utilizar menús, enlaces y formularios.

Debes poder identificar dónde está el foco y completar las tareas esenciales mediante teclado.

4.2. Zoom y adaptación

Amplía la página al 200 % y comprueba que el contenido sigue siendo legible y utilizable.

Reduce también la anchura de la ventana. La página debe reorganizarse sin perder funciones.

Ten en cuenta que los criterios de zoom y reflow tienen condiciones específicas: no basta con realizar una única comprobación para declarar conformidad.

4.3. Formularios y mensajes

Revisa si cada campo tiene una etiqueta comprensible, si se identifican los campos obligatorios y si los mensajes ayudan a corregir errores.

4.4. Contenido multimedia

Comprueba si los vídeos disponen de subtítulos cuando son necesarios, si los audios ofrecen las alternativas adecuadas y si los controles pueden utilizarse mediante teclado.

4.5. Lectores de pantalla

Los lectores de pantalla permiten comprobar cómo se anuncia la estructura, los enlaces y los controles.

Dos ejemplos son:

  • NVDA , disponible para Windows.
  • VoiceOver, integrado en dispositivos de Apple.

Aprender a utilizar un lector de pantalla requiere práctica. Una revisión inicial puede revelar problemas, pero no sustituye una evaluación con experiencia ni las pruebas con personas que utilizan estas tecnologías.

5. Easy Checks: tu primera revisión de accesibilidad

Easy Checks es un recurso del W3C/WAI que propone comprobaciones introductorias para comenzar a evaluar la accesibilidad de una página web.

No es una aplicación que instalamos ni un sistema que certifica automáticamente el cumplimiento de las WCAG.

Es una guía que ayuda a observar determinados elementos y a reconocer posibles barreras.

Consultar Easy Checks de W3C/WAI

5.1. Título y estructura

Comprueba que cada página tiene un título descriptivo y que sus encabezados organizan correctamente los contenidos.

El elemento title identifica el documento en la pestaña del navegador.

Los encabezados h1, h2 y siguientes ayudan a comprender la estructura del contenido.

5.2. Alternativas de imágenes

Revisa las imágenes informativas y comprueba que disponen de alternativas textuales adecuadas.

Las imágenes exclusivamente decorativas pueden utilizar alt="".

5.3. Contraste

Comprueba que los textos mantienen contraste suficiente respecto a sus fondos.

Para una medición inicial puedes utilizar WebAIM Contrast Checker, explicado anteriormente.

5.4. Teclado y foco

Recorre la página mediante Tab y Shift + Tab. Comprueba que los elementos interactivos son alcanzables, que el foco resulta visible y que no quedas atrapado en ningún componente.

5.5. Idioma de la página

Comprueba que el idioma principal está identificado mediante el atributo lang.

Ver ejemplo de código
<html lang="es">

Esta declaración ayuda a los navegadores y tecnologías de apoyo a interpretar el idioma.

5.6. Ampliación del contenido

Aumenta el zoom y comprueba si el texto, los enlaces y los controles siguen siendo utilizables.

5.7. Formularios

Revisa las etiquetas, las instrucciones y los mensajes de error.

Un placeholder no sustituye una etiqueta correctamente asociada.

5.8. Contenido audiovisual

Comprueba si los vídeos y audios disponen de alternativas adecuadas para la información que transmiten.

Actividad: revisión inicial con Easy Checks

Objetivo: realizar una primera comprobación manual de una página web.

  1. Selecciona una página propia o de ejemplo.
  2. Comprueba el título y los encabezados.
  3. Revisa las imágenes informativas.
  4. Navega con teclado y observa el foco.
  5. Amplía el contenido al 200 %.
  6. Comprueba el contraste de una combinación de texto y fondo.
  7. Revisa los formularios y mensajes si existen.
  8. Registra los problemas que encuentres.
Modelo de registro de comprobaciones
Comprobación Resultado Observación Mejora
Foco de teclado Necesita revisión Un botón no muestra un indicador visible. Revisar los estilos de foco y comprobar su contraste.

Resultado esperado: una tabla breve que recoja las comprobaciones realizadas, los problemas observados y las mejoras propuestas.

Si una comprobación no se aplica a la página o no encuentras problemas, indícalo sin inventar errores.

Recuerda: Easy Checks permite realizar una revisión introductoria. Superar estas comprobaciones no demuestra por sí solo conformidad WCAG.

6. WCAG-EM: una metodología de evaluación

Hasta ahora hemos aprendido a comprobar problemas concretos mediante herramientas y pruebas manuales.

Pero evaluar una web completa requiere organizar el trabajo: decidir qué vamos a revisar, seleccionar páginas representativas, aplicar comprobaciones y documentar los resultados.

Para ello podemos consultar la metodología WCAG-EM, desarrollada en el ámbito del W3C/WAI.

La versión 2.0, publicada como W3C Group Note en 2026, amplía el enfoque a productos digitales, además de sitios web.

Introducción oficial a WCAG-EM

Consultar documento técnico WCAG-EM 2.0

6.1. ¿Qué diferencia hay entre WCAG y WCAG-EM?

Diferencias entre criterios, herramientas y metodología
Elemento Función
WCAG Define criterios de accesibilidad.
WAVE, Lighthouse y otras herramientas Ayudan a detectar determinados problemas durante las comprobaciones.
Easy Checks Ofrece una introducción práctica a la revisión manual.
WCAG-EM Propone un procedimiento sistemático para organizar y documentar la evaluación.

6.2. Los cinco pasos de WCAG-EM

Podemos comprender la metodología mediante el ejemplo de nuestra biblioteca digital.

Fases de evaluación aplicadas a una biblioteca
Paso Qué hacemos Ejemplo
1. Definir el alcance Establecer qué producto se evalúa, el nivel WCAG de referencia y las condiciones. Evaluar la web pública de la biblioteca con un objetivo de nivel AA.
2. Explorar el producto Identificar sus vistas, funciones, tecnologías y procesos importantes. Examinar inicio, catálogo, búsqueda y renovación de préstamos.
3. Seleccionar una muestra representativa Elegir páginas, vistas y procesos que permitan revisar el producto de forma significativa. Incluir la búsqueda y un proceso completo de renovación, no solo la portada.
4. Evaluar la muestra Aplicar los criterios correspondientes combinando comprobaciones y juicio experto. Revisar teclado, formularios, alternativas y otros requisitos.
5. Documentar los resultados Registrar el alcance, las pruebas, los resultados y las limitaciones. Elaborar un informe con incidencias y evidencias.

En una aplicación completa de WCAG-EM es necesario seguir los requisitos detallados de la metodología, incluidos los relativos a selección de muestras y procesos completos.

Por tanto, esta explicación es una introducción educativa, no una sustitución del procedimiento oficial.

6.3. Documentar una evaluación

Un informe de accesibilidad debe permitir comprender qué se ha evaluado, cómo se ha realizado y qué problemas se han identificado.

Para cada incidencia conviene registrar:

  • La página o vista afectada.
  • La tarea o elemento revisado.
  • El problema detectado.
  • Cómo se ha comprobado.
  • Su posible impacto.
  • La solución propuesta.
  • El resultado de la nueva comprobación.

6.4. Herramienta para elaborar informes

El W3C ofrece una herramienta que ayuda a organizar los resultados de una evaluación.

Consultar WCAG-EM Report Tool

Es una referencia útil para conocer cómo se estructura un informe, aunque para comenzar podemos utilizar una tabla sencilla.

Importante: una práctica introductoria inspirada en WCAG-EM no equivale a una auditoría profesional completa.

7. Práctica final: evalúa y mejora una página web

Esta actividad integra los conocimientos de accesibilidad, usabilidad y desarrollo trabajados en el manual.

Objetivo

Analizar una página web, identificar posibles barreras, proponer mejoras y comprobar sus resultados.

Material necesario

  • Una página web propia o de ejemplo.
  • Un navegador.
  • Nu HTML Checker.
  • WAVE o Lighthouse.
  • WebAIM Contrast Checker.
  • Una tabla para registrar resultados.

Paso 1. Selecciona la página

Puedes utilizar una página de biblioteca, una web informativa o tu propio proyecto.

Si vas a realizar correcciones en el código, elige preferentemente una página que puedas modificar.

Paso 2. Define una tarea

Establece qué debería poder hacer una persona al utilizar la página.

Por ejemplo: "Encontrar el horario de la biblioteca y acceder al formulario de contacto".

Paso 3. Comprueba el teclado

Recorre la página utilizando Tab y Shift + Tab.

Observa si todos los elementos importantes son alcanzables y si el foco es visible.

Paso 4. Revisa el HTML

Utiliza Nu HTML Checker para revisar el marcado de la página.

Anota los errores relevantes y diferencia los problemas de sintaxis de los posibles problemas de accesibilidad.

Paso 5. Ejecuta una auditoría inicial

Utiliza WAVE o Lighthouse para detectar posibles barreras.

Selecciona los resultados más relevantes y estudia los elementos afectados.

Paso 6. Revisa el contraste

Selecciona una combinación de texto y fondo y comprueba su contraste mediante WebAIM Contrast Checker.

Paso 7. Comprueba la adaptación

Amplía la página al 200 % y reduce la anchura del navegador.

Observa si el contenido mantiene su funcionalidad y resulta comprensible.

Paso 8. Registra los resultados

Documenta los problemas que encuentres y explica por qué pueden afectar a las personas usuarias.

No inventes incidencias para completar una cantidad. Si no encuentras un problema en una comprobación, registra ese resultado.

Paso 9. Propón o realiza mejoras

Si puedes modificar la página, corrige uno o varios de los problemas detectados.

Si estás analizando una web ajena, redacta una propuesta de mejora justificada.

Paso 10. Vuelve a comprobar

Repite las comprobaciones afectadas por las correcciones y registra qué ha cambiado.

Modelo de informe

Registro de problemas y mejoras
Elemento Problema Comprobación Mejora Resultado posterior
Botón de envío No muestra foco visible. Navegación con teclado. Incorporar un indicador de foco adecuado. Pendiente de comprobar después del cambio.

Resultado esperado

Al finalizar, deberías disponer de un informe breve que identifique las comprobaciones realizadas, sus resultados y las mejoras propuestas o aplicadas.

El objetivo principal es aprender a razonar sobre los problemas y comprobar las soluciones, no conseguir una puntuación automática determinada.

8. Del desarrollo a la mejora continua

La accesibilidad y la usabilidad no se consiguen únicamente utilizando buenas herramientas.

Es necesario tomar decisiones adecuadas desde la planificación, implementar correctamente, comprobar el resultado y mejorar a partir de los problemas encontrados.

Proceso de trabajo: planificar → diseñar → desarrollar → evaluar → corregir → volver a evaluar.

Una web puede cambiar después de su publicación: se añaden páginas, formularios, imágenes y funcionalidades.

Por ese motivo, las revisiones deben formar parte del mantenimiento del proyecto.

La finalidad no es obtener una puntuación perfecta, sino ofrecer una experiencia que las personas puedan comprender y utilizar.

9. Autoevaluación
